# 基准测试方法论（怎么科学地测性能）

> 核心信条：**没有测量，就没有优化。** 凭感觉说"好像变快了"不算数，
> 数字才算数。这篇教你怎么得到可信的数字。

---

## 1. 为什么要"固定负载"

比较两次性能，必须用**完全相同**的输入，否则就像用两把刻度不同的尺子量东西。
所以 `tools/bench.py` 把负载写死了：

| 项          | 固定值                                 | 为什么                          |
|------------|-------------------------------------|------------------------------|
| prompt     | `[105538, 59975, 100132]`（"中国的首都是"） | 写死 token id，连 tokenizer 都不依赖 |
| decode 数量  | 32 个                                | 样本量足够算统计                     |
| 预热丢弃       | 前 4 个                               | 冷启动有抖动，丢掉才是稳态                |
| batch / 采样 | batch=1、greedy                      | 排除随机性                        |

**改负载 = 换尺子**。一旦改了，旧数字就不能再和新数字比。

## 2. 为什么用中位数，而不是平均或单次

单次测量会受很多噪声影响：CPU 频率波动、后台进程、温度降频。

- **中位数（median）**：抗离群点，最能代表"典型情况"。我们拿它当主指标。
- **p95**：95% 的请求比它快，反映"尾部有多差"，对延迟敏感场景重要。
- **min**：接近硬件理论上限，看"最好能到多少"。

`bench.py` 一次跑 32 个 decode token，丢掉预热 4 个，用剩下 27 个算这三个统计量。

## 3. 测量纪律（一次只改一个变量）

这是最重要的一条。想验证"INT8 量化让 matvec 变快"，就**只**改量化这一件事，
其他都不动，再测一次。如果同时改了量化、又改了线程数、又换了布局，
测出来变快了你也不知道是谁的功劳——**无法归因，等于白做**。

> 科学方法的套路：提出假设 → 只改变量 → 测量 → 对比 → 得出结论。

## 4. 怎么把测量对应到代码版本

性能数字必须能追溯到"是哪份代码跑出来的"，否则日志就是一笔糊涂账。做法：

1. **每个优化单独一个 commit**，commit message 写清"改了什么、为什么"。
2. 测完用 `git rev-parse --short HEAD` 记录当前 commit（bench.py 会自动记）。
3. 重要的里程碑打 **git tag**，如 `v0.1-fp32-baseline`、`v0.2-int8-w8a8`。

这样 `docs/optimization_log.md` 里的每一行都能一键跳回对应代码。

## 5. 怎么解释"为什么提升"

记录提升时，别只写"快了 3 倍"，要写**原因**。原因通常落在这几类：

| 类别   | 例子                                  |
|------|-------------------------------------|
| 减少搬运 | INT4 量化让权重体积 /8，decode 是带宽瓶颈，少搬数据就快 |
| 减少计算 | 用在线 softmax 把 3 遍扫描变 1 遍            |
| 并行   | 多线程把 matvec 切到多个核                   |
| 指令效率 | NEON 一条指令算 4 个 float                |

想找到原因，看 `bench.py` 输出的 **top op**：时间花在哪个算子，优化就该针对哪。
比如 fp32 基线里 `lm_head` 和 `down_proj` 是大头，说明 matvec 是主攻方向。

## 6. 标准操作流程

```bash
# 0. 改代码前，先测基线（如果还没有）
./scripts/bench.sh fp32-baseline

# 1. 实现你的优化（一个 commit）
git commit -m "perf: <改了什么> —— <为什么预期会快>"

# 2. 重新编译 + 测量，用优化命名
cmake --build build -j
./scripts/bench.sh <你的优化名>

# 3. 把输出里那行 Markdown 填上"提升多少/为什么"，追加到 docs/optimization_log.md
# 4. 一起提交，必要时打 tag
git add docs/optimization_log.md && git commit -m "bench: 记录 <优化名> 结果"
```

# 进阶：多个优化叠加时怎么评测

前面讲"一次只改一个变量"。但真实项目里你会有很多优化（NEON、多线程、
INT8……），最终要**叠加在一起用**。这时出现两个新问题：

1. 每个优化到底**贡献了多少**？（归因）
2. 叠加后是不是**简单的加速比相乘**？（交互）

## 7. 最大的坑：加速比不能直接相乘

很多人以为"NEON 2× × 多线程 4× = 8×"，实测往往达不到，因为**多个优化
可能在抢同一个资源**。

定义**交互系数**来量化这件事：

```text
交互系数 = 实测的组合加速比 / (各优化单独加速比的乘积)
  > 1   → 协同：叠加后更快（少见）
  ≈ 1   → 独立：各干各的，理想情况
  < 1   → 竞争：互相拖累（很常见！）
```

拿我们的场景举个具体例子：

- **NEON** 提升的是"算得快"（计算吞吐）；
- **多线程** 提升的是"并行算"（多核同时干）；
- 叠加时：NEON 让每个线程更快算完 → 于是更快撞到**内存带宽**这堵墙 →
  这时候再加线程也搬不进更多数据 → 多线程的实际收益被打折。

所以 NEON × 多线程 常常 **小于** 各自的乘积。**组合的收益必须实测，
绝不能拍脑袋把几个加速比相乘。**

## 8. 用"优化栈"记录：两个加速比都要写

每个配置都是"基线 + 若干优化"组成的**栈**。日志里把栈写明，并记**两个**加速比：

| 配置（优化栈）         | decode 中位 | vs 原始基线 | vs 上一配置 | 交互说明                                     |
|-----------------|----------:|--------:|--------:|------------------------------------------|
| fp32-scalar（基线） |    230 ms |   1.00× |       — | —                                        |
| + NEON          |    150 ms |   1.53× |   1.53× | —                                        |
| + NEON + 4 线程   |     55 ms |   4.18× |   2.73× | 预期 1.53×4≈6.1×，实测 4.18×，交互系数≈0.69 → 撞带宽墙 |

- **vs 原始基线**：回答"总共快了多少"（用户视角，对外汇报用这个）。
- **vs 上一配置**：回答"这一步新加的优化贡献了多少"（归因视角）。
- **两个都要记，缺一不可**：只看前者无法归因，只看后者看不出总量。

## 9. 组合评测的三条纪律

**纪律一：每加一个优化，重新 profile。**
Amdahl 定律的另一面——你把当前瓶颈优化掉后，**瓶颈会转移到别处**。
NEON 把 matvec 算快后，top op 可能变成 attention 或 KV 搬运。所以下一刀
砍哪，要看 `bench.py` 输出的最新 top op（它是指南针）。

**纪律二：组合爆炸时只测"增量路径"。**
N 个优化理论上有 2^N 种组合，不可能全测。实用做法：

- 只测增量序列：基线 → +A → +A+B → +A+B+C，每步记 vs-上一配置
  （这正是你最终要的真实叠加顺序）。
- 只有**怀疑某两个优化打架**时，才专门测那一对（如 {NEON}、{线程}、
  {NEON+线程} 三个点），算交互系数。
- 不要为"全面"去测所有组合，那是浪费。

**纪律三：每个配置可独立复现。**

- 每个配置一个独立 commit/tag，能 checkout 回去复测。
- 换配置**必须重新干净编译**，别让旧二进制混入别的优化。
- 配置命名清晰可读：`fp32-scalar` / `fp32-neon` / `fp32-neon-mt4` / `int8-neon-mt4`。
