# 基准测试方法论（怎么科学地测性能）

> 核心信条：**没有测量，就没有优化。** 凭感觉说"好像变快了"不算数，
> 数字才算数。这篇教你怎么得到可信的数字。

---

## 1. 为什么要"固定负载"

比较两次性能，必须用**完全相同**的输入，否则就像用两把刻度不同的尺子量东西。
所以 `tools/bench.py` 把负载写死了：

| 项 | 固定值 | 为什么 |
|---|---|---|
| prompt | `[105538, 59975, 100132]`（"中国的首都是"） | 写死 token id，连 tokenizer 都不依赖 |
| decode 数量 | 32 个 | 样本量足够算统计 |
| 预热丢弃 | 前 4 个 | 冷启动有抖动，丢掉才是稳态 |
| batch / 采样 | batch=1、greedy | 排除随机性 |

**改负载 = 换尺子**。一旦改了，旧数字就不能再和新数字比。

## 2. 为什么用中位数，而不是平均或单次

单次测量会受很多噪声影响：CPU 频率波动、后台进程、温度降频。
- **中位数（median）**：抗离群点，最能代表"典型情况"。我们拿它当主指标。
- **p95**：95% 的请求比它快，反映"尾部有多差"，对延迟敏感场景重要。
- **min**：接近硬件理论上限，看"最好能到多少"。

`bench.py` 一次跑 32 个 decode token，丢掉预热 4 个，用剩下 27 个算这三个统计量。

## 3. 测量纪律（一次只改一个变量）

这是最重要的一条。想验证"INT8 量化让 matvec 变快"，就**只**改量化这一件事，
其他都不动，再测一次。如果同时改了量化、又改了线程数、又换了布局，
测出来变快了你也不知道是谁的功劳——**无法归因，等于白做**。

> 科学方法的套路：提出假设 → 只改变量 → 测量 → 对比 → 得出结论。

## 4. 怎么把测量对应到代码版本

性能数字必须能追溯到"是哪份代码跑出来的"，否则日志就是一笔糊涂账。做法：

1. **每个优化单独一个 commit**，commit message 写清"改了什么、为什么"。
2. 测完用 `git rev-parse --short HEAD` 记录当前 commit（bench.py 会自动记）。
3. 重要的里程碑打 **git tag**，如 `v0.1-fp32-baseline`、`v0.2-int8-w8a8`。

这样 `docs/optimization_log.md` 里的每一行都能一键跳回对应代码。

## 5. 怎么解释"为什么提升"

记录提升时，别只写"快了 3 倍"，要写**原因**。原因通常落在这几类：

| 类别 | 例子 |
|---|---|
| 减少搬运 | INT4 量化让权重体积 /8，decode 是带宽瓶颈，少搬数据就快 |
| 减少计算 | 用在线 softmax 把 3 遍扫描变 1 遍 |
| 并行 | 多线程把 matvec 切到多个核 |
| 指令效率 | NEON 一条指令算 4 个 float |

想找到原因，看 `bench.py` 输出的 **top op**：时间花在哪个算子，优化就该针对哪。
比如 fp32 基线里 `lm_head` 和 `down_proj` 是大头，说明 matvec 是主攻方向。

## 6. 标准操作流程

```bash
# 0. 改代码前，先测基线（如果还没有）
./scripts/bench.sh fp32-baseline

# 1. 实现你的优化（一个 commit）
git commit -m "perf: <改了什么> —— <为什么预期会快>"

# 2. 重新编译 + 测量，用优化命名
cmake --build build -j
./scripts/bench.sh <你的优化名>

# 3. 把输出里那行 Markdown 填上"提升多少/为什么"，追加到 docs/optimization_log.md
# 4. 一起提交，必要时打 tag
git add docs/optimization_log.md && git commit -m "bench: 记录 <优化名> 结果"
```
